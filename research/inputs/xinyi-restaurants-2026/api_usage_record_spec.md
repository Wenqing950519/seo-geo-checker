# API 使用量保存規格

版本：v1.0  
核准日期：2026-07-18  
適用範圍：2026 台北市信義區餐飲 AI 搜尋能見度研究

## 目的

每次正式 GeoCheck 白皮書批次須獨立備份 API 呼叫數、輸入 Token、輸出 Token、總 Token、成功率、延遲與成本估計，供方法揭露、研究成本評估與重跑核對。使用量資料不得影響 GEO 分數、提及率、官網引用率或任何研究結論。

## 每批必要檔案

- `api-usage-events.jsonl`：逐次 API 事件，包含 run ID、時間、供應商、模型、操作、狀態、Token、延遲與錯誤階段。
- `api-usage-summary.json`：依研究 run ID 彙總的呼叫量、Token、成功率、供應商／模型分組、成本估計與事件檔 SHA-256。
- `methodology.json`：記錄使用量檔名、run ID 與事件檔 SHA-256。
- `mock-api/usage-events.jsonl`：專案全域原始帳本；只作備援，不直接作為單一研究批次的引用值。

## 白皮書揭露位置

方法章「模型、執行環境與 API 使用量」應彙總：

- 研究 run ID。
- Perplexity 與 Gemini 的實際請求數。
- 成功／失敗請求數與成功率。
- 輸入、輸出與總 Token。
- 若費率已設定，列出估算美元成本；明確標註為依設定費率計算，非供應商帳單。
- 使用量事件檔 SHA-256。

逐次事件不放在正文，保存於研究資料附錄或可下載資料包。Token 使用量只用於成本與可復現性描述，不解讀為模型品質或網站能見度。

## 中斷與續跑

- 正式命令必須固定 `--run-id`。
- 同一資料集續跑使用相同 run ID，使事件可合併；不同研究批次不得共用 run ID。
- 若批次中斷，先從全域帳本按 run ID 匯出備份，再繼續執行。
- 最終發布前須核對使用量事件數、批次規劃呼叫數與實際失敗紀錄；重試呼叫需保留，不得刪除。
